# OCR 機能の設計

## Context

現在、TransMenuアプリケーションにはメニュー写真をアップロードする機能が実装されている。
画像はPostgreSQLデータベースの`menu_photos`テーブルにバイナリデータとして保存され、
`/api/menu-photos`エンドポイントでアップロード・取得が可能である。

既存のOpenAI API統合は`src/lib/openai.ts`にあり、`getOpenAIClient()`関数で
クライアントを取得できる。`/api/chat`エンドポイントでテキストベースの
OpenAI API呼び出しが実装されている。

フロントエンドはNext.js App Routerを使用し、`MenuPhotoUpload`コンポーネントで
画像のアップロードと一覧表示を実現している。Emotionを使用したCSS-in-JSで
スタイリングされている。

## Goals / Non-Goals

**Goals:**

- アップロード済み画像からテキストを抽出できる
- OpenAI Vision APIを使用した高精度なOCR処理
- 非同期処理によるUIの応答性維持
- 適切なエラーハンドリングとユーザーフィードバック
- 既存のコードベースとの一貫性を保った実装

**Non-Goals:**

- 画像の前処理や後処理（回転、トリミングなど）
- 抽出テキストの自動保存やデータベースへの保存
- 複数画像の一括OCR処理
- OCR結果の編集機能
- リアルタイムOCR（画像選択時の自動実行）

## Decisions

### Decision 1: サーバーサイドAPIエンドポイントの作成

**選択:** `/api/ocr`エンドポイントを新規作成

**理由:**

- OpenAI APIキーをクライアントサイドに露出させないため
- 画像データの処理をサーバーサイドで行うことでセキュリティを確保
- 既存のAPIエンドポイントパターン（`/api/menu-photos`、`/api/chat`）と一貫性を保つ

**代替案:**

- クライアントサイドで直接OpenAI APIを呼び出す
  - 却下理由: APIキーの露出リスク、CORSの問題

### Decision 2: 画像の受け取り方法

**選択:** 画像IDのみをサポート（リクエストボディに`imageId`を含める）

**理由:**

- アップロード済み画像のみを対象とする要件に合致
- シンプルな実装で済む
- データベースから既存の画像を取得するパターンと一貫性がある

**実装方法:**

- `imageId`が存在する場合: データベースから画像を取得し、base64に変換
- `imageId`がない場合: 400エラーを返す

**代替案:**

- ファイルとIDの両方をサポート
  - 却下理由: アップロード済み画像のみを対象とする要件に合わない

### Decision 3: OpenAI Vision APIの使用方法

**選択:** `gpt-4o`または`gpt-4o-mini`モデルを使用（環境変数`OPENAI_MODEL`で設定可能）

**理由:**

- 既存の`DEFAULT_MODEL`設定を活用
- Vision API対応モデルを使用
- コストと精度のバランスを考慮

**プロンプト設計:**

```text
この画像に含まれるすべてのテキストを抽出してください。
メニューの場合、料理名、価格、説明などを含めてください。
テキストは元の配置や構造を可能な限り保持してください。
```

**代替案:**

- 専用のOCRプロンプトを複数用意する
  - 却下理由: 初期実装ではシンプルに保つ

### Decision 4: 画像のbase64エンコーディング

**選択:** 画像をbase64文字列にエンコードしてOpenAI APIに送信

**理由:**

- OpenAI Vision APIがbase64エンコードされた画像をサポート
- 既存の画像データ（Buffer）から簡単に変換可能

**実装方法:**

```typescript
const base64Image = buffer.toString('base64');
const dataUrl = `data:${mimeType};base64,${base64Image}`;
```

**代替案:**

- 画像URLを提供する
  - 却下理由: 画像がデータベース内にあり、公開URLがない

### Decision 5: フロントエンドの状態管理

**選択:** 既存の`useState`パターンを継続使用

**理由:**

- 既存のコンポーネントとの一貫性
- シンプルな状態管理で十分

**追加する状態:**

- `extractedText: string | null` - 抽出されたテキスト
- `processingOcr: boolean` - OCR処理中フラグ
- `ocrError: string | null` - OCRエラーメッセージ

**代替案:**

- 状態管理ライブラリ（Zustand、Reduxなど）を導入
  - 却下理由: 現時点では過剰

### Decision 6: UI配置

**選択:**

- アップロード済み画像の各アイテムにOCRボタンを配置
- 抽出テキストはテキストエリアで表示（選択・コピー可能）

**理由:**

- 直感的なUI配置
- 既存のデザインパターンとの一貫性
- アップロード済み画像のみを対象とする要件に合致

## Risks / Trade-offs

### Risk 1: OpenAI APIのレイテンシ

**リスク:** API呼び出しに数秒かかる可能性があり、ユーザー体験に影響

**対策:**

- ローディングインジケーターを明確に表示
- 非同期処理でUIをブロックしない
- タイムアウト処理を実装（30秒程度）

### Risk 2: APIコスト

**リスク:** GPT-4 Vision APIの使用によりコストが発生

**対策:**

- 環境変数でモデルを選択可能にし、`gpt-4o-mini`をデフォルトに設定
- 必要に応じてレート制限を実装可能な設計

### Risk 3: 大きな画像ファイルの処理

**リスク:** 大きな画像ファイルのbase64エンコーディングに時間がかかる

**対策:**

- 既存のファイルサイズ制限（10MB）を適用
- 必要に応じて画像のリサイズを検討（将来の拡張）

### Risk 4: OpenAI APIのエラーハンドリング

**リスク:** APIキー不足、レート制限、サービス障害など

**対策:**

- 適切なエラーメッセージをユーザーに表示
- サーバーサイドでエラーログを記録
- リトライロジックは実装しない（シンプルに保つ）

### Trade-off: 精度 vs コスト

**選択:** `gpt-4o-mini`をデフォルトとし、必要に応じて`gpt-4o`に変更可能

**理由:** 初期実装ではコストを抑えつつ、必要に応じて精度を向上できる柔軟性を確保

## Migration Plan

この機能は新規追加であり、既存機能への影響はない。

**デプロイ手順:**

1. 環境変数の確認（`OPENAI_API_KEY`が設定されていること）
2. `/api/ocr`エンドポイントのデプロイ
3. フロントエンドコンポーネントの更新
4. 動作確認

**ロールバック:**

- フロントエンドの変更を元に戻す
- `/api/ocr`エンドポイントを削除
- データベーススキーマの変更は不要

## Open Questions

1. **OCR結果の保存:** 将来的にOCR結果をデータベースに保存する必要があるか？
   - 現時点では非目標とする

2. **レート制限:** APIコストを抑制するためのレート制限を実装するか？
   - 初期実装では実装しない。必要に応じて後で追加

3. **画像の前処理:** 低品質な画像の前処理（コントラスト調整など）を実装するか？
   - 初期実装では実装しない。必要に応じて後で追加

4. **多言語対応:** 日本語以外の言語のOCR精度を向上させるためのプロンプト調整
   - 初期実装では汎用的なプロンプトを使用。必要に応じて言語別プロンプトを検討
